# R47: an inherited workload is lost when the intermediate parent exits

**What changed.** `src/submeter/attribution/rules.py`: the `Attributor` keeps a map from `ProcessKey` to (exe, command line, attribution) across batches. `assign()` takes `exited`, the keys to forget (the caller passes `batch.exited`). Kernel group membership is still checked first, every batch. Otherwise a process whose exe and command line are unchanged keeps its remembered attribution, so an inherited workload lasts for the life of the process even after its parent exits or it is re-parented. After an exec, a rule that matches the process itself (or a Submeter pid) wins, and the move is listed in `Attributor.changes` as (key, from, to), reset on each `assign()`; the caller writes it with the existing `RawFile.record_event`, so `raw.py` is not edited (the collector loop that will call it is planned). No retry on a rules or settings change: under R149 that restarts the program, which builds a new `Attributor`. Seeding the map at start is I29's open question and is not in this commit.

**Test.** `tests/test_attribution.py::test_an_inherited_workload_lasts_for_the_life_of_the_process`: a rule-matched shell (`bash`, workload `agent`) has three children. In batch 2 the shell is gone: one child keeps a stale parent pid, one is re-parented to pid 1 `systemd`, which a `services` rule matches by parent, and one execs into `postgres`, which a `db` rule matches by exe. The first two stay in `agent`, the third moves to `db`, and `changes` lists that move. A third call with `exited` forgets the re-parented child, which is then resolved afresh.
