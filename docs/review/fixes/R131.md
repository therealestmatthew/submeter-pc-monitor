# R131: daily_minimums applies one UTC offset to every reading

**What changed.** `src/submeter/analysis/growth.py` `daily_minimums()` drops `utc_offset_s`. Each reading's local day comes from `datetime.fromtimestamp(t, UTC).astimezone()`, which takes the offset from the operating system at that moment, and each day starts at its local midnight (`datetime.combine(day, time()).timestamp()`). No new dependency. `tests/test_baseline.py::test_usual_range_and_daily_minimums` asserted UTC days, which this changes; it now builds its two days from local midnights (`datetime(2026, 11, 20).timestamp()`), so it holds in any zone. The plan said to pin `TZ=UTC` there; `time.tzset` does not exist on Windows, so a pinned test would depend on the Windows machine's zone, and a zone-independent test was the smaller change that passes on both.

**Test.** `tests/test_analysis.py::test_local_days_follow_the_daylight_saving_change`: with `TZ` set to Europe/London's rule (`GMT0BST,M3.5.0/1,M10.5.0`, so no zone files are needed) and `time.tzset()`, readings at 00:30 BST on 25 October 2026, 23:30 GMT the same day and 00:30 GMT on 26 October give two days: 25 October (25 hours, starting 23:00 UTC on 24 October) with minimum 3.0, and 26 October with 7.0. Skipped on Windows, where `time.tzset` does not exist.
