# R71. One-instance lock on Windows: the OS may release a dead holder's lock late and acquire() tries once

**What changed.** `src/submeter/store/files.py` `InstanceLock.acquire(wait_s=5.0)`: when refused, it retries every 100 ms until `wait_s` has passed; one try is now `_take()`. `holder()` was fixed under R105 (I43), so this commit keeps R71's retry and test items only. `tests/test_baseline.py`: the refused `acquire()` calls in `test_file_map_names_expiry_and_lock` and `test_the_windows_lock_makes_the_calls_windows_expects` pass `wait_s=0`, and the first test checks the lock file is empty with `stat().st_size == 0` instead of reading the locked byte through a second handle. `scripts/platform_check.py` `check_lock`: the same two changes, and after killing the holder it polls for the lock for up to 5 s instead of sleeping 0.5 s once.

**Test.** `tests/test_files.py::test_acquire_waits_for_a_lock_freed_late`: a second `InstanceLock` starts `acquire(wait_s=1.0)` while the first holds the lock, and a timer releases it 0.3 s later; the second acquires it.

`check_lock` run alone on Linux: `PASS  one-instance lock: first holder ['True'], second process ['False'] and it read the holder's pid: True, this process refused: True, lock file left empty: True, free after the holder was killed: ['True']`, in 5.4 s; the refused second process in `HOLD` (G1's lines) now waits the default 5 s.
