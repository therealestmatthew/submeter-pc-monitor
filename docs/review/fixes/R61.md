# R61: aggregate() labels a polled sum 'kernel' for any workload in kernel_workloads

**What changed.** `src/submeter/core/models.py` gains a frozen `GroupTotals` record after `Finding`: `cpu_s`, `io_read_bytes` and `io_write_bytes` as `int | None`, and `processes`. In `src/submeter/attribution/rules.py`, `aggregate()`'s `kernel_workloads` is now a mapping from workload to its group's `GroupTotals`, in place of a set of names. A workload in it reports the group's CPU, process count and, when the group can read it, I/O, labelled `kernel`, even when polling saw none of its processes. Its polled sum is no longer reported; the test keeps it as the cross-check (the other workloads still sum to their processes). `tests/test_baseline.py` lines 268-272 assert the group's figure and limit the conservation assertion to polled workloads.

**Limits.** When the group cannot report I/O (`None`), the workload keeps its polled I/O sum, because `WorkloadSample`'s I/O fields are plain `int` (`models.py:144-145`) and cannot say unavailable. `source` names the CPU accounting path, as I7's assumption (a) states. Memory and `started` still come from polling.

**Known breach of "unavailable, never zero".** The checker found that the fallback above produces a zero for an unavailable figure. If polling saw none of a tagged workload's processes, the polled sums are empty, and the record built from a fresh `_Total()` says `io_read_bytes=0`, `io_write_bytes=0` and `memory_bytes=0` beside the group's process count. The checker's probe, run here before the follow-up commit:

```
GroupTotals(cpu_s=0.5, io_read_bytes=None, io_write_bytes=None, processes=3), no polled processes:
{'taken_at': 1000.0, 'interval_s': 1.0, 'workload': 'agent:run', 'source': 'kernel', 'cpu_s': 0.5, 'memory_bytes': 0, 'io_read_bytes': 0, 'io_write_bytes': 0, 'processes': 3, 'started': 0}
```

Before R61 such a workload was not emitted at all, so this zero is new. It breaks the AGENTS.md rule "A metric the system cannot deliver is reported as unavailable, never as zero". It is not a harmless fallback. It cannot be fixed in G4's files: `WorkloadSample` belongs to G2, and R42's planned task makes its I/O fields `int | None`, after which `aggregate()` passes `None` through from `GroupTotals`. The memory zero needs R46's planned `memory_total_bytes: int | None`. Until then, the comment at the fallback in `aggregate()` names the breach, and so does the request to G2 and to R42's task. The integrator should not integrate R61 without either the `WorkloadSample` change or the owner's acceptance of this breach. The follow-up commit changes no behaviour, so it has no failing test. It changes 5 lines in `rules.py` (4 added, 1 removed): a three-line comment replaces the inline one. R61 now totals 43.

**Order with R39 (G2).** R39 adds `gap=batch.gap` to the `WorkloadSample(...)` call in `aggregate()`; this commit leaves that call untouched. A three-way `git merge-file` of rules.py, models.py and test_baseline.py against fix-g2 at `fb3073c` reported 0 conflicts, and the merged `aggregate()` holds both changes.
