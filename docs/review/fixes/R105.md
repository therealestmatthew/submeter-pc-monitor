# R105. The lock's pid file outlives a crashed holder, so a pid-based daemon stop could signal an unrelated process

**What changed.** `src/submeter/store/files.py` `InstanceLock`: `acquire()` writes `pid create_time` to the pid file, with the start time from psutil (R56's integer stamp replaces it when R56 lands, I43). `holder()` returns the pid only when the live process with that pid has that start time and a new private `_held()` probe finds the lock taken: a non-blocking try-lock on a second handle fails, or on Windows opening the lock file fails. A free lock, a dead pid, a reused pid or an unreadable file gives `None`. `tests/test_baseline.py` (`test_the_windows_lock_makes_the_calls_windows_expects`): the msvcrt stand-in's expected calls gain one `(2, 1, 0)`, the probe `holder()` makes while `first` holds the lock (I43). The docs/17 Operations sentence is the docs worker's.

**Test.** `tests/test_files.py::test_holder_names_only_the_live_holder_of_a_held_lock`: a holder takes the lock and its handle is closed without `release()`, as when it crashes, so the lock is free and the pid file stays; `holder()` gives `None`. Then a held lock whose pid file names this process with a start time one second off also gives `None`.
