# Build Submeter: a per-workload PC performance monitor

## What this is and why

I run many AI coding agents and heavy desktop apps at the same time, and I can't tell which of them is costing me what. I want a monitor I trust enough to make decisions from. It has three jobs, all served from one data set. When something has to be cut, they rank in this order, attribution highest:

1. Attribution: what does each workload (an agent run, a browser, an IDE, a build) cost in CPU, memory, I/O and GPU?
2. Live diagnosis: why is the machine slow right now?
3. Trends: how does behaviour drift over days and weeks, and where are the leaks and regressions?

Build it as a long-running local service with a CLI and a self-contained HTML report. A live web dashboard, and the local API it needs, come in version 1.1. Windows 11 is the target of version 1, and only Windows gets the platform layer: kernel accounting, the launcher and its holder, system counters and autostart. Linux must work from the same codebase, polled: there `submeter run` reports that tagged runs are unavailable and runs the command polled, and CI on a Linux runner runs the portable tests. Put everything OS-specific behind provider interfaces from the first commit, so the Linux platform layer can be added after version 1.

Version 1 only observes. It must never change a process's priority or affinity, suspend it, or kill it. Placing a process tree that Submeter itself launches into a Job Object or cgroup for accounting is allowed. Setting any limit on that group is not. A control layer will come later, so shape analysis output as plain data objects a future policy engine could consume.

## Priorities

When goals conflict, resolve them in this order:

1. Never show a wrong number. When a metric is unavailable, record it as unavailable. Never substitute zero or an estimate. Every figure shown to me should be traceable to how it was measured.
2. Stay inside the overhead budget.
3. Cover more metrics.
4. Add features.

## Stack and conventions

- Python 3.13 or newer for everything in version 1, managed with uv. From 3.13, `time.monotonic()` on Windows uses QueryPerformanceCounter, at 1 microsecond, instead of a clock that steps in 15.6 ms, which would put about 6% of error on a 250 ms interval. Ruff for lint and format. mypy in strict mode. pytest with pytest-asyncio.
- Pydantic v2 for all config, sample and finding models, with extra="forbid" and frozen=True.
- SQLite in WAL mode. Typer for the CLI.
- Report: `submeter report` writes one self-contained HTML file, with its script and data inline and a meta Content Security Policy, so no Node toolchain is needed. Draw its charts with a canvas chart library such as uPlot.
- psutil is the fallback and the cross-check on Windows, not the hot path there. On Linux in version 1 it is the process reader, and the overhead guard lengthens the intervals.
- Store timestamps in UTC. Measure intervals on a monotonic clock that keeps counting during suspend: CLOCK_BOOTTIME on Linux, and on Windows QueryPerformanceCounter, which `time.monotonic()` uses from Python 3.13.
- Before using any OS API you are not certain about, check current documentation instead of relying on memory. This applies most to Job Objects, cgroup v2 delegation, Windows performance counters, NVML, and psutil, whose API has changed across major versions.

## Architecture

Five layers with data flowing one way: providers, sampler, attribution, store, analysis. The CLI and the report are thin readers over store and analysis. Each layer must be testable in isolation from recorded fixtures.

### Three programs, one contract

Three programs share nothing but files on disk, and each writes only its own:

- submeter-collector: providers, sampler, attribution, redaction. It writes the raw files and nothing else.
- submeter-server: rollups, retention, analysis, alerts. It writes the history file, and reads the raw files, the session marker files and the final run files, deleting each run file once it has copied it into the history file.
- the launcher, `submeter run`: starts a tagged process tree and writes one small run file for it.

`submeter session start` and `stop` write the session marker files, which the server reads. None of the three programs writes them.

None of the three imports another, and every file has exactly one writer. The reason is that the collector is the hot path, and I want to be able to replace it with a Rust binary later without touching anything else. In phase 0, run the collector (snapshot, deltas, attribution and raw-store writes) for 10 minutes on my Windows machine, as the bulk-snapshot probe under How to work says. If, for 300 processes at the default intervals with the provider that will ship, its CPU time as a share of one core is over the overhead budget (3% active, 1% idle), or its private bytes are over 80 MB, stop and tell me, because that is my trigger for the Rust collector. The psutil fallback's figures are reported, not judged.

### Collection: two accounting paths

Agents spawn thousands of processes that live for less than a second, and polling cannot see them. If children live 300 ms on average, a 1-second poll captures under a third of their CPU time. So use two paths, and label every workload with the one that measured it.

Kernel accounting, for tagged workloads. `submeter run --as NAME [--label LABEL] -- COMMAND` launches the command inside a named Windows Job Object (nested jobs), and records the group in a run file. The launcher sets SUBMETER_RUN in the command's environment to the id of the run, so an agent inside it can read its own run's cost with `submeter cost --run "$SUBMETER_RUN" --json`. NAME is a stable workload name that is reused across runs, such as agent:refactor. LABEL identifies one run. Time series are kept per name and totals per run, so a new label never starts a new series. Warn in `doctor` when there are more than 200 distinct workload names. On Windows the job's totals are authoritative for CPU time, I/O and process counts, including processes that have already exited. The job also gives peak commit (PeakJobMemoryUsed), and no current memory. Current memory for a tagged group is the sum of USS over its members (JobObjectBasicProcessIdList) that have a reading, labelled partial with the count of members without one, and shown with the age of the reading like any other workload.

On Windows the launcher creates the command inside the job with PROC_THREAD_ATTRIBUTE_JOB_LIST through CreateProcessW (ctypes), so no descendant is born outside the group and nothing is created suspended. Starting the command with subprocess and assigning it to the job afterwards lets children it starts at once escape the group. The launcher itself stays outside the job, so its own CPU time counts as Submeter's. It never joins the job: a process in a job that forbids breakaway can never leave it, so a holder started after such a join would sit inside the job it waits to empty.

A group's counters disappear when the group does, so:

- The launcher writes the run file when it creates the group, in the live state. It holds the group open while the command runs and passes the command's exit code through. When the group is empty, the launcher, or its detached holder below, replaces the run file by atomic rename with the final state, which holds the group's totals. A tagged run is therefore accounted for even if the collector was not running.
- `submeter run` must return when the command returns, even if the command left background processes behind. Those processes stay in the group, so something has to keep the group open until it is empty and then save the final totals: a small detached holder, which is the launcher's own detached part. The holder keeps a handle to the job until the job's count of active processes (ActiveProcesses) is 0, and then writes the final state by atomic rename, only after the launcher's last write, so the run file keeps one writer. The collector never writes a run file and is never the holder: on Windows a job can be opened by name only while some handle to it is open, so a restarted collector could not find a job that only it had held. If no handle survives, the run's totals are lost: a reader that finds the run file still live and cannot open its job reports them as lost, never as zero. The launcher, the holder and the collector run in the same logon session, because the collector opens the job by name, and a job named without the `Global\` prefix is visible only in the session that created it.
- The collector finds live groups from the run files in the live state and reads their totals each tick. After a restart it re-attaches to every live group.
- Set no limits on the group. Do not allow breakaway and do not set kill-on-close. Forbidding breakaway is the job's default, not a limit, and it keeps every descendant in the group, including the grandchildren that Node-based agents start, which break away silently from Node's own job. The cost: a program that asks to break away from the tagged job, or that places children in its own job with UI limits, cannot start those children under `submeter run`. This is a known limit.

Nested runs. If `submeter run` starts inside a tagged group, the run file records the parent run. The outer launcher sets SUBMETER_RUN in the command's environment, and the inner launcher reads it from its own environment and confirms that it is inside the outer job with IsProcessInJob, against that job opened by name. The variable can be lost, for example through sudo, env -i or a sandboxed agent shell: when it is missing, the run file records the parent as unknown. A process belongs to its innermost group. A parent's reported totals are its kernel totals minus the totals of the tagged runs that name it as parent, so each CPU-second belongs to one workload. Every reader that reports a parent's totals subtracts them: `submeter cost --run` over run files from phase 1, and the collector's reading of live groups from phase 3.

Linux tagged runs (after version 1). Version 1 builds kernel accounting on Windows only. On Linux, `submeter run` reports that tagged runs are unavailable and runs the command polled, so its workload is labelled polled. The design kept for later: the launcher starts the command inside a cgroup v2 and records the group in the run file. `cpu.stat` is always readable, because it needs no cpu controller, and the memory and pids files only where the parent slice passes those controllers down. The holder, final-totals, re-attach and nested-run rules above apply to the cgroup in the same way, and so does the launch rule: the command is in the group before it runs, so no descendant starts outside it. The gate's reference there is the load generator's children's summed CPU time from wait4 or RUSAGE_CHILDREN, and membership is checked in `cgroup.procs`. On Linux the kernel gives a tagged group CPU time and memory only: the user's systemd delegates the cpu, memory and pids controllers and not io, so without root there is no `io.stat`, and no file counts processes started (`pids.peak` counts threads, so it is never used for one). Processes started is unavailable for a tagged run. Its I/O comes from the launcher, which reads its own `/proc/self/io` after waiting for the command, because the I/O of reaped children folds into the process that reaps them. That figure is labelled partial, and `doctor` states the gap: processes still running when the command returns, and double-forked orphans, which the user's systemd adopts. For a tagged group on Linux, the figure comparable with USS is `memory.stat` anon plus `memory.swap.current`, sampled by the collector. `memory.current` and `memory.peak` include page cache and kernel memory: store the peak labelled "charged memory, includes file cache" and never add it to PSS or USS.

After version 1, on Linux, ask the signed-in user's systemd over the user bus for a transient scope with `Delegate=` set to the controllers its slice already passes down (see the controller rule below). Inside it make leaf groups: `holder` for the waiting process and `payload` for the command; `payload` passes its controllers down and runs the command in `payload/main`, so a nested run can make a sibling under `payload` with the same files. A nested run under `payload` is counted in the outer `payload`'s files, so the outer run's reported totals are `payload`'s totals minus those of the tagged runs nested in it, and each CPU-second belongs to one workload. The holder watches `payload/cgroup.events`; when `populated` is 0 it reads `cpu.stat`, `memory.peak`, `memory.stat` and `pids.peak`, writes the run file's final state and exits, and systemd removes the scope. For a live tagged group, take memory from the group's `memory.stat` rather than reading `smaps_rollup` for each member, whose cost grows with resident memory. Never make cgroups outside such a scope: systemd owns every cgroup it has not delegated, and a cgroup made with mkdir stays after it empties. With no user bus (su, sudo -u, cron, a system service, WSL without systemd), say that tagged runs are unavailable and run the command polled.

After version 1, on Linux, delegate to the run's scope only controllers its parent slice already passes down (read the parent's `cgroup.subtree_control` first), normally memory and pids. Never enable the cpu or io controller anywhere and never write `cpu.weight` or `cpu.max`: enabling a controller turns it on for every sibling group, and `cpu.stat` is present without it. So never use `Delegate=yes`, which delegates every supported controller. Where the parent passes nothing down, set `Delegate=` to an empty list, which turns delegation on with no controllers. This keeps fixed rule 1: a controller turned on for the sibling groups changes how the user's other programs share CPU, and exposes settings that would cap or reprioritise them.

After version 1, on Linux, a tagged tree can leave its group, because Linux cannot forbid that as a job that forbids breakaway does on Windows: a descendant started through systemd-run, or through a snap or flatpak launcher, moves to a scope of its own. Polling still attributes such a process through its parent, and the run file says the kernel total excludes it. A launcher that finds itself in a tagged group, from its own `/proc/self/cgroup`, nests by making a sibling of `payload/main` inside the outer `payload` and moving itself there, so the inner run counts in the outer payload's kernel total, from which the rule above subtracts it. When this path is built, Known limits gains a row for descendants started through systemd-run, snap or flatpak launchers.

Bulk polling, for everything else. Do not walk processes one at a time on the hot path. Every tick, read the cumulative CPU and I/O counters and the memory gauges of every process. Read the costly fields on a slower cadence: USS or PSS at the USS interval, for the largest processes only; the working folder only when a rule uses it, at the USS interval; and the command line as each system's passage below says. The default active interval of 2 s fits the overhead budget only with a direct reader, such as the Windows bulk snapshot. With psutil the overhead guard lengthens the interval. Polled workloads are labelled as polled, with a note that short-lived children may be undercounted.

On Windows, take one system-wide process snapshot per tick that returns CPU times, memory counters, I/O counters, thread and handle counts for every process. Microsoft documents that call as subject to change, so fall back to psutil if it fails, report the provider as partial while the fallback is in use, and keep a CI test that fails loudly if the snapshot stops parsing. CPU times, start time and I/O are members Microsoft documents only as Reserved, and psutil's Windows path uses the same call for thread counts and for processes it cannot open, so the fallback reduces the dependency but does not remove it. The CI parse test is the guard. The fallback does not read thread counts on Windows, because psutil makes one whole-system query for each process's count, so threads are unavailable while it is in use. Read a process's command line once, when it is first seen, because a Windows process cannot start running a different program. To read command lines, open other processes with PROCESS_QUERY_LIMITED_INFORMATION only, never PROCESS_VM_READ, and use NtQueryInformationProcess (ProcessCommandLineInformation). psutil reads command lines through the process environment block, which needs more access, so that read is a known exception while the fallback is in use. Two other reads need more access than the command-line read: a process's working folder can be read only from its process environment block, which needs PROCESS_VM_READ, both directly and through psutil; and psutil reads USS by querying the process's working set, for which it opens the process with PROCESS_QUERY_INFORMATION. Exclude pid 0, the System Idle Process, whose CPU time is the machine's idle time. Pid 4 (System) and the Registry, MemCompression and Secure System processes belong to System.

On Linux, version 1 polls through the psutil provider, and the direct /proc reader comes after version 1. psutil measured about 95 ms per tick, store writes included, at 300 processes on Linux, so there the overhead guard holds the active interval at about 3.2 s or longer and the idle interval at about 9.5 s or longer. Read command lines again at the USS interval, because a process can exec another program, or rewrite its title, under the same pid and start time. Recover reaped children's CPU time and I/O from the counters of the process that reaps them, without counting a child twice. Read each process's child time (cutime plus cstime) and credit its increase to that process. Its `/proc/<pid>/io` counters already include the I/O of every child it has reaped. When a child that polling saw is reaped, subtract the child's last-seen CPU time and child time, and its last-seen I/O counters, from the next increase of the process that reaped it: the child's last-seen parent, or the subreaper if that parent has ended. Keep a zombie in the snapshot while its /proc entry exists, because its CPU time is still readable; a zombie counted there must not be counted again from its parent's child-time counters after it is reaped. Tie the subtraction to the reaping, not to the child's last sighting, so an exited child must stay in the snapshot until it is reaped. This recovers descendants reaped inside the tree, and charges orphans to the subreaper's workload. Never recover more CPU time in an interval than busy time less the CPU time already credited. The children it cannot recover are listed under Known limits. Test it with a fixture of nested reaping, through the psutil provider. The direct /proc reader, after version 1, leaves the command line unread for a process whose real user id differs from the collector's and marks that process restricted, with a test.

Rules for both paths:

- Providers return cumulative counters. The sampler computes rates from deltas, so a change of cadence never loses or invents CPU time. Every sample records the interval it covers. A counter a provider cannot read is None, never a stand-in zero, and a provider never writes a stand-in start time. When either reading of a process's CPU time is None, the sampler has no baseline and credits that process no CPU for the interval, as for an older process seen for the first time. Cap every per-process CPU delta at the interval times the logical cores, and count the capped samples.
- Detect suspend and resume. Suspend is the growth of a clock that counts sleep over one that does not: CLOCK_BOOTTIME minus CLOCK_MONOTONIC on Linux, QueryPerformanceCounter minus QueryUnbiasedInterruptTime on Windows. Neither needs administrator rights. Read the clock that stops during suspend only for this test and for awake seconds, never to time an interval, because on Windows it is accurate only to a system clock tick, up to 15.625 ms. A tick is also a gap, a stall, when its interval is longer than three times the interval the collector meant to wait plus 2 s of slack; no fixed length makes a gap, because the settings with the battery multiplier allow intervals up to 600 s, and the overhead guard lengthens intervals. Record a gap. A gap keeps its CPU and I/O deltas: the counters are cumulative, so the deltas are exact, and a suspended process accrues nothing. The gap flag controls only how the interval's time is counted, so a gap never shows as one giant sample.
- Stamp each batch with the wall time read at an anchor plus the time elapsed since on the interval clock, so a suspend never makes a stamp lag, and stamps never go backwards. When the wall clock departs from the stamp by more than the 2 s slack and the suspend test does not fire, the wall clock was stepped: record a 'clock stepped' event, which starts an epoch, not a gap, so the interval keeps its CPU and its coverage. After a step forward, re-anchor. The rule after a step back, and for slow drift between the two clocks, is an open question for the owner: re-anchoring would move stamps backwards, and keeping the anchor leaves them ahead of the wall clock for the rest of the run.
- Identify a process by pid plus start time. The start time in a process identity is the platform's integer stamp: on Linux, field 22 of /proc/PID/stat (ticks since boot) with /proc/sys/kernel/random/boot_id; on Windows, CreateTime as a FILETIME integer. On Linux the psutil provider reads field 22 itself, because psutil gives only a wall-clock float worked out from the boot time, which moves when the clock is stepped. Convert to wall time only for display. Compare start times, and test whether a process was born in an interval, on the boot clock. Treat a parent link as valid only if the parent started before the child. Windows CreateTime is the system time at creation, so there a wall-clock step back can still put a child before its parent; the step is recorded as an event, as above, and Known limits says so.
- A process whose command line or owner cannot be read, the inputs that decide its workload, is counted in a Restricted bucket with whatever is visible. It is never dropped. A workload figure that only some of its processes can give is a partial sum, marked with the count of processes missing it, and one that none of them can give is unavailable, never zero. A process whose start time cannot be read has no identity, because a pid alone never identifies a process, so it appears only in a per-snapshot count of unreadable processes, which `doctor` and the reconciliation show beside Restricted. A failure reading one process never costs the whole snapshot: a failed optional read, of I/O, the command line or the working folder, leaves that field unavailable, and a process that fails to read at all is counted as above. psutil keeps one object per pid between calls, so when a pid it still lists is reported gone, the object may belong to an earlier process that held the pid: the psutil provider reads that pid again through a fresh object in the same tick, or the process that took the pid is missed for two ticks and then credited no CPU for them.
- WSL2 and Docker Desktop appear on Windows as a single VM process. Show it as its own workload labelled opaque, and report its share of busy CPU time, and of capacity, in `doctor`. A collector inside the guest is not in version 1.

Memory: collect units that can be added across processes. Workload totals use USS (or PSS on Linux) so shared pages are not counted twice. USS is expensive, so read it on a slow cadence and only for the largest processes, and show the age of the reading. A workload's memory total is therefore the sum over its processes that have a reading, marked partial with the count of processes without one. For growth and leak detection use private bytes on Windows and RSS plus swap on Linux, because Windows trims working sets under pressure and USS then falls for a process that is still leaking. Keep the two units in separate fields: the growth unit for every process each tick, and the total unit with the time it was read. A Job Object keeps no current memory figure, so a tagged group's current memory is also the sum of USS over the members that have a reading, labelled partial with the count of members without one. The job's peak commit is stored under that label and never added to USS or shown as current memory.

System-wide, on Windows: per-core load and frequency, commit and available memory, paging split into reads and writes, disk latency, run queue and the on-battery flag. Detect throttling from processor frequency and performance counters. Do not use psutil for frequency on Windows, where it reports only a nominal value. On Linux, version 1 reads only per-core load, available memory and the on-battery flag, through psutil. PSI and the other Linux system counters come after version 1. A CPU-second is not a fixed amount of work, because efficiency cores and reduced frequency do less with it. Report CPU time as measured and show processor frequency beside it. Do not normalise workload figures in version 1.

Extended providers, each declaring its capability at the current privilege level (full, partial with what is missing, or unavailable with why). Version 1 has two:

- GPU load per process. On Windows use the GPU Engine counters. Engine percentages do not add across engine types, so report per engine type and use the busiest as the headline. Open counters by their English names so a localised Windows does not break them. On Linux use NVML for NVIDIA, and per process the DRM fdinfo engine counters (`drm-engine-*`) where the driver provides them, which the kernel documents for i915 and xe; they show the user's own processes only. amdgpu's `gpu_busy_percent` gives load for the whole device, not per process.
- VRAM per adapter, used and total. The GPU-bound verdict reads it to rule itself out when VRAM is full.

Other extended providers (after version 1). No job's acceptance check or verdict reads them, so version 1 does not build them. The design kept for later:

- VRAM per process. On Windows the GPU Process Memory counter is the only per-process source, because NVML reports the figure as unavailable under the desktop driver model. Microsoft documents a fault in which that counter over-reports. Before it is used, compare the sum of per-process values with the adapter total over time. If they drift, mark the provider partial and keep leak detection off per-process VRAM.
- Temperatures and battery level. Temperatures through hwmon on Linux. Windows has no dependable unprivileged temperature source. Battery level on both.
- Network per process. Connection counts and remote endpoints per process, and bytes per interface. Per-process byte counts need administrator rights.

### Attribution

Every process maps to exactly one workload, in this order: kernel group membership, then rules, then inheritance from a valid parent, then Unattributed.

- Rules live in rules.toml and match on executable file name, process name, command-line pattern, parent chain or working directory, with explicit priority. Do not match on environment variables, because reading another process's environment is unreliable.
- A process keeps the workload it was given for its whole life, so an inherited workload survives the exit of the parent it came from. Rules are tried again only when a later reading shows that its executable or command line changed, as after an exec. A rule that then matches the process itself wins, and the change of workload is recorded as an event in the raw file. Kernel group membership and Submeter's own processes still come first. When the collector starts, it seeds what it remembers from the open raw file's process table and workload-change events, for processes still running, and then runs the rules again.
- A tagged workload reports its group's kernel totals for CPU time, I/O and process count, not the sum of its polled processes. That sum is kept only as a cross-check and for the process tree.
- System, Restricted, Unattributed and Submeter itself are always-visible workloads.
- System is CPU time the kernel spends that no rule, tagged run or other workload can claim. On Windows it is the System process (pid 4) and the Registry, MemCompression and Secure System processes, plus interrupt and DPC time. On Linux it is the kernel threads, which have PF_KTHREAD set in the flags field of /proc/PID/stat, plus irq and softirq time. These rows are left out of the per-process figures, so they are not counted twice. System is read from these counters, never taken as a remainder.
- Busy time is each core's time that is not idle, with interrupt and DPC time counted once; on Windows phase 0 checks whether system time already includes them. Idle is the per-core idle time (on Linux, idle plus iowait). Pid 0 on Windows is not read as a process.
- CPU time not seen by polling is busy time less the reported workload totals, which for a tagged workload are the kernel totals it reports, less System. It is mostly short-lived processes that polling missed. Store it with each sample beside the machine's busy time, as a machine-level figure and not a workload, so no rule or `submeter run --as` can claim it.
- On Linux, also place CPU time not seen by polling by cgroup. Each tick, read `cpu.stat` in every leaf cgroup, which needs no privilege. Its increase less the polled deltas of the processes in that cgroup is CPU time not seen by polling in that unit. When one workload owns all of that cgroup's processes, charge it to that workload and show it as not seen by polling in the unit. Otherwise leave it in the not-seen term, never in System. Phase 0 measures the per-tick cost of these reads on the Linux CI runner; if it breaks the overhead budget, Linux keeps only the total.
- Reconciliation invariant: for any window, attributed plus unattributed plus system plus restricted plus not seen by polling plus idle CPU time equals total capacity within 2%. Test it, including a quiet fixture on which CPU time not seen by polling stays under a share stated with the fixture. Show all six terms in `submeter why` and in the report.

### Store

Data that expires together lives in a file together, so retention is always a file delete. Each file is SQLite in WAL mode with one writer.

- Raw files, one per UTC day, written by the collector: every sample at full resolution, the processes seen that day, and their redacted command lines stored once each. Kept 48 hours.
- One history file, written by the server and kept: hourly buckets, hourly summaries per workload and executable, runs, sessions and their summaries, findings and epochs.
- Run files, one small JSON file per tagged run, written by the launcher with an atomic rename: live when the group is created, and final, with the group's totals, once the group is empty. The collector reads the live ones. The server copies each final run file into the history file's run table and then deletes it. `submeter cost --run` reads the run table and any run file not yet copied.
- Session marker files, one small file per session, written by `submeter session start` and `stop` with an atomic rename and read by the server. They replace an API call, because version 1 has no API.

Rules for raw files:

- Workload totals are written every sample, and each workload and system row carries its batch's gap flag and awake seconds. Per-process rows are written only when a value changes beyond a threshold, plus a full snapshot of every live process at the start of each file and every 10 minutes, so no query looks back further than that.
- A closed day's file is never written again and never migrated, even when the wall clock steps back across midnight. Open closed files only for the length of a query, so they can be deleted on Windows.
- Process rows live only in raw files. Nothing keyed by pid is kept beyond 48 hours.

What every hourly bucket records:

- for counters (CPU seconds, bytes read and written, processes started): the sum;
- for gauges (memory, process count, GPU load, frequency, run queue): minimum, maximum, time-weighted mean and last value;
- for CPU cores in use and for memory: a fixed-bin histogram that can be merged, so a percentile over any period comes from merged bins and never from averaging percentiles;
- covered seconds, sample count and active seconds, so a gap is never read as zero use. A gap sample goes whole into the bucket that holds its end, adds its CPU, I/O and processes started to the sums, and adds nothing to covered seconds, the sample count, active seconds, the memory mean or the histograms. A bucket with no covered seconds is valid, and closing or merging one must not divide by zero;
- awake seconds, the growth of the clock that stops during suspend. CPU and I/O rates and capacity in core-seconds are worked out over awake seconds, so a stall's CPU, which its gap keeps, never raises a rate above capacity. Covered seconds stay the observed time for the memory mean, the histograms and the coverage rule under Queries;
- the capacity at the time (logical cores, memory) and an epoch id.

Build hourly buckets from raw data while it still exists. Rollups are idempotent: recomputing a bucket gives the same row. A bucket is final 30 seconds after it ends.

Summaries that must outlive the raw data:

- When a session stops or a tagged run ends, store its exact totals per workload: CPU seconds, peak and mean memory, I/O, processes started and top executables. `cost` and `diff` read these. For a tagged run, CPU seconds, I/O and processes started come from the job when the run ends; mean memory comes from the collector's samples and is unavailable for a run the collector never saw; and the peak taken from the job is stored as peak commit.
- Each hour, store the top 10 executables per workload by CPU time and by peak memory, keyed by executable name and never by pid. Keep these one year.

Epochs. An epoch is a stretch of time in which the sampling intervals, the rules file, each provider's status, the hardware and the Submeter version all stayed the same. Any change starts a new epoch with a stated reason. A wall-clock step that the collector detects also starts a new epoch. The collector records such events in the raw file and the server turns them into epochs. Never rewrite stored history when rules change.

Queries. Answer from raw samples, merged to wider steps, while they cover the start of the window, and otherwise from hourly buckets. Return the tier and resolution with every result. Charts draw the minimum-to-maximum envelope. Leave buckets with less than half their time covered out of baselines and trends. Work out days and weeks in my time zone at query time, from buckets stored in UTC.

Operations:

- Put files in the platform's standard per-user locations for settings, data and state, with SUBMETER_HOME overriding all of them. `submeter store status` prints every file with its writer, size and coverage.
- One-instance lock per program. Rotating logs, 5 files of 5 MB each, with the same redaction as the store.
- Durability: synchronous=NORMAL. A crash or power loss may lose up to 5 seconds of samples and must never corrupt a file. Keep read transactions short so the write-ahead log can be checkpointed, and truncate it at each checkpoint.
- At start, run an integrity check on the history file. Quarantine a damaged raw file, record a gap and carry on.
- Back up the history file daily with SQLite's online backup and keep 3 copies. Migrate it only after a backup. Every file carries a schema version, and readers accept the current and previous versions.
- Enforce the disk budget, default 2 GB, across all files. When over budget, delete the oldest raw file first, never going below 24 hours, then backups down to one, then raise a finding. Never delete history automatically.
- Export to JSON and CSV.

### Privacy and local security

Command lines often contain keys and tokens. Redact them before they are written: keep the executable and a pattern-scrubbed argument list, with a configurable redaction list and a strict mode that stores the executable only. Restrict every data file to the current user. On Linux the system lets any user read other users' command lines: keep only the name of another user's process, never its command line, and count the process as Restricted.

Version 1 opens no network port: the CLI reads the store files directly, and the API with its token comes in version 1.1. `submeter cost --json` and the report must never contain command lines or working directories. Nothing leaves the machine. Version 1 has no webhook, upload or update check. Both programs run as the signed-in user and never request administrator rights.

### Analysis

Detectors emit findings: type, severity, confidence, workload, time window, and the evidence that triggered them.

- Leak: sustained growth by a robust slope such as Theil-Sen, over a minimum duration, with no plateau. Growth that levels off is a warm-up and must be cleared. Track growth at workload level too, so a leak that spans short-lived processes is still seen. With default settings, a leak of 75 MB an hour must be flagged within 2 h 5 min. That rate is set clearly above the default minimum slope of 50 MB an hour, because growth at exactly the minimum slope is flagged only about half the time once the readings are noisy. Run this check on raw workload rows, merged on read into 1-minute steps of time-weighted means, over up to 48 hours or the raw data on disk, whichever is shorter. Judge nothing until the data spans the minimum duration. The baseline's plateau test compares the slope of the last third of the points with a quarter of the whole window's slope, so noise in a flat tail can flag a warm-up, and the flat stretch between the steps of a leak that grows in steps can clear it. Replace it in phase 4 with a test that does not compare a short, noisy tail with a fraction of the whole window's slope, for example one that needs a minimum tail span, or one that compares a point estimate of the tail slope with the minimum slope. Tune it together with the 75 MB an hour acceptance: a test that needs the tail slope's lower confidence bound to clear the minimum slope flags that leak only about 38% of the time with noise of up to 40 MB either way on each 1-minute step.
- Bottleneck verdict for a window: CPU-bound, memory-bound, I/O-bound, GPU-bound, thermally throttled, no bottleneck or inconclusive. The verdict table in How it decides is the single rule set: check every rule; one matching rule is the verdict; no matching rule, with at least 60 seconds of data, is no bottleneck; two or more matching rules, or a rule that matches while its ruled-out condition holds, mean the signals disagree. Give each threshold an on value and a lower off value, so the verdict does not flicker. Judge throttling against the base (nominal) frequency, not the turbo maximum. Always include a confidence level and the evidence. Inconclusive is a correct answer when signals disagree. On Windows judge memory pressure from commit and page writes, not from hard faults alone.
- Runaway process count.
- Session diff: compare two sessions or periods and rank what changed. Read the stored summaries, and flag any comparison of maxima or percentiles that crosses a change of sampling interval.

Each detector needs a fixture that triggers it and at least one quiet fixture that must not, including a cache warm-up for the leak detector. Write the leak detector's fixtures as raw workload rows with noise: the browser warm-up in How it decides, with noise of up to 40 MB either way on each sample, is a quiet fixture, and a leak that grows in steps of 256 MB every 2 hours is a trigger fixture. A warm-up written without noise passes the baseline's plateau test and hides its fault.

Slow growth and baseline anomaly (after version 1). Version 1 has neither, and has no spike or swap-storm check. Regressions are found by hand with `submeter diff` and the hourly history. The design kept for later:

- Slow growth: on the hourly tier, fit at least 7 daily minimums of memory, which needs 8 days of hourly buckets, against a minimum slope of its own below the leak check's, for example 5 MB an hour. This catches leaks too slow for the leak check; with the leak check's 50 MB an hour it would flag nothing that check misses. Its trigger fixture is a leak of 10 MB an hour over 8 days.
- Baseline anomaly: keep baselines separately for idle and active states, using median and MAD with a floor on spread, computed from hourly buckets. An hourly bucket is active when its active seconds are at least half of its covered seconds, a sample being active when the workload uses at least 0.005 of one core, and each baseline uses only buckets of its own state. The usual range is built from the values of the trailing 14 days that were not flagged. The value compared with the range is one per local day, the daily peak: the highest hourly maximum for memory and the highest hourly 95th percentile of cores in use for CPU. The floor bounds the MAD before it is scaled and is set per metric, for example 0.03 GB of memory and 0.05 cores, so an idle series still gets a range of non-zero width. Raise an anomaly only when 3 values in a row are outside the range. Raise nothing until a learning period has enough samples. Hold the baseline still while an anomaly is open, so a regression does not become the new normal. The history file's `baseline` table is added by a migration with this feature.

## Configuration

Settings live in submeter.toml and attribution rules in rules.toml. Both load into frozen Pydantic models with unknown keys rejected. Precedence: command-line flag, environment variable, file, built-in default. Durations and sizes are written as strings such as "1s", "48h", "2GB".

Sampling settings and defaults:

- mode = adaptive (or fixed)
- active_interval = 2s (allowed 250ms to 10s)
- idle_interval = 5s (1s to 60s)
- idle_after = 60s
- uss_interval = 30s, uss_top_n = 25
- gpu_interval = 2s
- on_battery_multiplier = 2
- overhead_limit: idle 1%, active 3%

Other settings: storage (retention for raw and executables, disk_budget, change_threshold, keyframe_interval 10m, backups to keep), analysis (leak min_duration 2h and min_slope 50MB/h), verdict (window 5m, per-signal thresholds with on and off values, min_confidence), alerts (rules, cooldown 15m), attribution (rules_file, inherit_from_parent, unattributed_alert, max_workload_names 200), privacy (redaction scrub or exe_only, extra patterns) and providers (enabled list).

Alert rules are structured fields: a workload pattern, a metric, above or below, a value, a duration and a severity. Do not invent a rule language to parse. An alert rule may name only these metric ids: cpu_cores, memory_bytes, processes and io_bytes_per_s for any workload, commit_fraction and throttled for the reserved workload `machine`, and overhead_fraction for the workload `submeter`. Refuse any other. Three rules ship built in: commit_fraction above 0.90 for 2 minutes (serious), throttled for 5 minutes (warning), and overhead_fraction above 0.03 for 5 minutes (warning). On Linux, version 1 reads no commit counter, so commit_fraction is unavailable there in version 1 and the commit rule reads unavailable instead of firing. After version 1, read commit_fraction on Linux only when vm.overcommit_memory is 2, because only then does the kernel enforce the commit limit, and report it unavailable otherwise. After version 1, when PSI is read, add a Linux-only machine metric memory_pressure_full, and on Linux the built-in rule uses memory pressure (PSI memory full) instead.

Behaviour:

- Reject out-of-range values with the allowed range in the error. Never clamp silently.
- Settings and rules are read when a program starts, and never while it runs. `submeter config reload` restarts the collector and server: it stops them as `daemon stop` does and starts them as `daemon start` does, which on Windows runs the scheduled task.
- `submeter config show --effective` prints every value with its source. `submeter config check FILE` validates without applying.
- A restart starts a new epoch only if something that defines an epoch (see Epochs under Store) has changed. The epoch is marked on the charts, so a shift in the data can be traced to a settings change.
- The overhead guard outranks the configured interval. If the limit is exceeded, lengthen the collector's intervals and raise a finding. Stretch uss_interval or shrink uss_top_n before lengthening the active and idle intervals: on Linux the USS reading costs about 25 to 30 ms of CPU per GB resident in the processes read.

Not configurable: observe-only behaviour, running without administrator rights, sending nothing off the machine, the rule that `submeter cost --json` and the report never contain command lines, and the rule that unavailable metrics are never estimated.

## Interfaces

CLI, where every command accepts --json with a stable schema:

- `submeter daemon start|stop|status|install|uninstall`, installing a Windows scheduled task at logon, set up as below (a systemd user unit for Linux, which also runs the installed entry point, comes after version 1)
- `submeter run --as NAME [--label LABEL] -- COMMAND`
- `submeter top`, `submeter why`, `submeter cost`, `submeter diff A B`
- `submeter findings` to list findings, newest first
- `submeter session start|stop|list`, where start and stop write the session's marker file
- `submeter report` for a self-contained HTML report, which holds version 1's charts for a session or range
- `submeter export` to JSON or CSV
- `submeter config show|check|reload`, where reload restarts the collector and server
- `submeter store status|check|backup`
- `submeter rules test` to show which rule claims a given process
- `submeter doctor` for the capability matrix, restricted-process count, disk usage and the collector's own cost, and on Linux whether /proc is mounted with hidepid

`submeter why` must answer in under two seconds.

On Windows, `daemon install` registers a scheduled task for the current user only: a logon trigger with LogonType InteractiveToken, so the task runs only while the user is signed in and stores no password; DisallowStartIfOnBatteries=false and StopIfGoingOnBatteries=false, so it starts and keeps running on battery; ExecutionTimeLimit=PT0S, so it is not stopped after the default 72 hours; MultipleInstancesPolicy=IgnoreNew; restart on failure; and Priority 5 (normal) instead of the default 7 (below normal), so the collector is not starved under the load it is there to diagnose. Fixed rule 1 covers the processes Submeter observes, not Submeter itself, so setting its own task's priority does not break it. The task runs the installed entry point, not `uv run`. Alerts have thresholds and cooldowns. A firing alert rule raises a finding, which `submeter findings`, `submeter why` and the report show. Desktop notifications come after version 1.

Agents get their cost from the CLI: an agent started with `submeter run` reads its own run's cost with `submeter cost --run "$SUBMETER_RUN" --json`. An MCP server is not in version 1.

## Known limits to show, not hide

Version 1 cannot measure some things. Say so in the CLI output, in the report and in `doctor`, beside the numbers they affect, instead of leaving a gap that looks like a zero:

- Work done for a workload by another process, such as the Docker daemon, a shared language server or a browser that was already open, is charged to that other process.
- Polled workloads undercount short-lived children on Windows, and on Linux for children that are orphaned, not yet reaped, or whose parent ignores SIGCHLD.
- On Windows, a program that asks to break away from a tagged group, or that places children in its own job with UI limits, cannot start those children under `submeter run`.
- On Linux, tagged runs are unavailable in version 1: `submeter run` runs the command polled. PSI and the other Linux system counters are not read either, so `why` on Linux reads Inconclusive or unavailable.
- The WSL2 and Docker Desktop VM is opaque: version 1 has no guest collector.
- Workload memory totals can lag by up to the USS interval.
- On Windows, after a wall-clock step back, a child started within the step of its parent can appear to start before it, so its parent link is refused.
- CPU time is not normalised for core type or frequency.
- Which files a process reads or writes is not recorded, only bytes and handle counts.
- Temperatures, per-process VRAM and network figures are not collected in version 1. On Windows, temperatures and per-process network bytes would also need administrator rights.

## Overhead budget

The monitor must not become the problem. The budget covers every Submeter process: the collector, the server and the launcher's detached holders. Attribute all of them to the submeter workload, not just one pid. With 300 processes running, their summed CPU time stays under 1% of one core at idle cadence and under 3% at active cadence, and the collector and server together stay under 150 MB of memory, measured as private bytes on Windows and USS on Linux. The overhead guard acts on the collector's intervals, and overhead_fraction reports the total. If cadence and budget conflict, slow the cadence. Measure the collector's whole tick, and one USS round for the 25 largest processes, in phase 0, as the bulk-snapshot probe says, and tell me if these numbers are unrealistic before building on them.
